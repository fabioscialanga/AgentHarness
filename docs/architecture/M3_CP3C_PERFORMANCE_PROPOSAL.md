# M3 — proposta prestazionale per CP3-C (nessuna implementazione)

**Stato:** proposta da revisionare. CP3-B non è collegato all'hook Codex. Le misure di riferimento sono negli artifact `M3_CP3A_*_EVAL.json` e `M3_CP3B_PERF_WINDOWS.json`.

## Costo osservato

La detection CP3-A usa 2–7 invocazioni Git per caso, 253 sulle 37 fixture (media 6,84). Il matching CP3-B richiama oggi la detection **due volte** per evitare che un cambiamento concorrente produca `covered`: 14 processi Git per matching nel caso misurato, oltre alla detection che il futuro handler dovrebbe già aver fatto per trovare il rischio. Su Windows la sonda CP3-B precedente alla correzione dell'interprete ha misurato p50/p95 620,939/742,902 ms; le nuove letture dell'eseguibile vanno rimisurate nel benchmark CP3-C. Questi numeri non sono latenza dell'hook né confronto con M2.

## Riduzione proposta, preservando il controllo delle corse

1. **Riutilizzare la prima cattura già necessaria alla detection.** Nel singolo evento Stop, la detection produce `StateIdentity` e un timestamp monotono. Il matcher riceve quella cattura; non avvia una seconda detection *iniziale* identica. Dopo aver letto gli artifact, ricattura lo stato e richiede identità esatta. Un mutamento fra detection e matching, durante la lettura o subito prima dell'uscita resta `unknown:state_changed`. La protezione ABA rimane limitata come nel contratto. Nel caso misurato, il matching scenderebbe da 14 a **7** invocazioni Git; l'intero percorso detection+matching da 21 a **14**, prima di altri risparmi. L'API dovrà rifiutare un risultato senza root/contesto della cattura o con deadline scaduta; nessun risultato di un evento precedente diventa riutilizzabile.
2. **Unire le due letture `rev-parse`.** `git rev-parse --show-toplevel HEAD` può restituire root e commit con un solo processo, mantenendo la validazione del root. È un risparmio potenziale di **una chiamata per cattura**. Occorre testare output, SHA-1/SHA-256 Git e worktree su Windows/Linux prima di cambiare la canonicalizzazione. Il `state_id` deve rimanere identico sui casi congelati; se non è possibile, serve un contratto versionato e una revisione separata.
3. **Gating M2 prima della detection.** Dopo `disable`, ritorno immediato senza Git M3. L'handler M2 già individua i path modificati: se `pyproject.toml` non è fra i path pertinenti, nessuna detection DEP o lettura artifact. Per un cambio non tracciato, il gating deve includere la verifica mirata del solo `pyproject.toml`; non può ignorarlo per risparmiare tempo. Nessun polling, daemon, test o LLM.
4. **Letture artifact progressive, senza fidarsi delle cache.** Se `.agentharness/runs` non esiste, restituire `uncovered` dopo il controllo finale dello stato. Se esiste, esaminare candidate entro i budget. Hash, snapshot e report necessari a `covered` restano obbligatori; mtime o cache non sostituiscono i byte. L'eseguibile attestato va controllato prima e dopo la decisione, senza usare un percorso fornito da un artifact per leggere file arbitrari.

## Gate sperimentale CP3-C

Misurare almeno 30 eventi appaiati per caso su Windows e Linux: disabled, nessun cambio DEP, cambio DEP senza artifact, con artifact valido e con artifact alterato. Registrare p50/p95 dell'intero hook e dei segmenti detection/Git/matching/I/O, numero di processi Git, byte letti, messaggi e eventuali token mostrati dall'host. Confrontare sulla stessa macchina e versione Codex con M2. **Non integrare automaticamente** se il percorso enabled senza rischio supera la soglia incrementale approvata di 50 ms p95, se disabled introduce nuove chiamate Git o se qualsiasi ottimizzazione produce un falso `covered` nelle prove di corsa, manomissione o contraddizione. La riduzione dei processi è una previsione da verificare, non una misura acquisita.
